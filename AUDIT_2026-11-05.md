# Repository audit — 2026-11-05

## Scope and safety

This audit was performed against the `main` branch. Implementation is applied only to
`mverify-mcore-audit-2026-11-05`. No RTL, project data, or `main` branch files were changed.

## Confirmed repository facts

- Root `app.py` imports the root `mverify.core` package.
- A second source tree exists at `mverify/mverify/core`. It is not the package imported by
  the current root application. Do not delete or merge it until its history and intended
  packaging role are established.
- The UI caption reports Mverify v0.8.0 while the repository `mverify/VERSION` reports
  v0.10.0. README version references also differ.
- Mcore API health reports v0.4.0.
- Mcore's Ollama client and API route defaults previously embedded
  `qwen2.5-coder:7b`.
- The current UVM generator is explicitly a passive compile/topology scaffold. The
  generated driver and monitor contain TODO sections. The scoreboard has no reference
  model comparison. No functional verification or PCIe compliance claim is supported.
- RTL parsing is regex-based structural extraction, not full SystemVerilog parsing,
  elaboration, or UHDM analysis.
- Requirement classification and mapping are heuristic evidence. They do not prove
  that a requirement is implemented by the matched RTL.
- Existing project scanner comments state that it does not produce protocol compliance
  or functional pass/fail results.

## Changes in this branch

- Make Mcore Ollama URL and model defaults configurable through `MCORE_OLLAMA_URL`
  and `MCORE_MODEL`.
- Keep per-request `model` and `ollama_url` overrides.
- Improve JSON response validation in the Ollama adapter.
- Expose configured model and Ollama URL from the Mcore health endpoint.
- Add this audit so the current engineering limits are visible.

## Validation still required

- Run Python unit tests and compile checks in the repository's supported environment.
- Run Mcore health and model-list checks with the user's local Ollama daemon.
- Run Surelog (if installed) against representative DUT filelists.
- Run generated UVM output through VCS/UVM 1.2 and inspect compile diagnostics.
- Compare UVM monitor transactions against independently derived expected results.
- Validate PCIe requirements against the exact licensed specification revision used by
  the project.
- Resolve the duplicate source tree and version policy with repository history and CI.

## Not implemented by this audit

This commit does not add a universal SystemVerilog frontend, protocol-compliant PCIe
stimulus, a functional reference model, automatic simulator diagnosis, or model training.
Those require staged design work and test evidence. A generated UVM skeleton must not
be presented as a working protocol testbench.
